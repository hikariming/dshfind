# 第 1 課：プラグインとは結局何なのか？

> **一言でいうと**：DSH プラグインとは、**`apply` 関数をエクスポートする 1 つのファイル**です。起動時にフレームワークが `ctx` という「万能電源タップ」を手渡してくれるので、あなたはそこに何か（ツール、UI、ポリシー）を差し込みます。差し込んだものは、プラグインのアンロード時に**すべて自動的に抜き取られます**。考え方はこれだけです。

## 1. すでに出会ったことのあるプラグインから始めよう

おそらく、次のようなものは使ったことがあるはずです：

| 見たことがあるもの | 何をしているか |
|---|---|
| ブラウザ拡張機能（広告ブロッカー） | 完成済みのブラウザに機能を**追加**する |
| VSCode プラグイン（テーマ、言語サポート） | 完成済みのエディタに機能を**追加**する |
| スマホアプリ | 完成済みのスマホ OS の上にインストールされる |

これらには共通点があります：**本体は出来上がっていて、プラグインは横に貼り付けるパッチにすぎない**ということです。ブラウザ拡張機能は、アドレスバーやタブバー、レンダリングエンジンには手を出せません——それは「コア」であり、ハードコードされています。

DSH は違います。**DSH には、手を出せないコアというものが存在しません。**

---

## 2. DSH の違い：ソフトウェアそのものがプラグインで組み立てられている

DSH のアーキテクチャドキュメントの 1 行目にはこう書かれています：

> **すべてはプラグインであり、ループも例外ではない。**

「ループ」とはエージェントのメインループ——「少し考える → 1 つ行動する → また考える」というあのサイクルのことです。他のフレームワークではこれがコアであり、変更できません。DSH では**これもプラグインの 1 つ**であり、差し替えが可能です。

つまり、次のものはすべてプラグインで、立場は完全に対等です：

- どのモデルを使うか → プラグイン
- モデルが呼び出せる各ツール → プラグイン
- コマンドをどこで実行し、ファイルに触れてよいか → プラグイン
- チャット履歴をどこに保存するか → プラグイン
- いま見ている Web インターフェース → 数十個のプラグイン
- **先ほどのメインループ** → これもプラグイン

> 🎁 たとえるなら：他のフレームワークは**完成した建物**です——間取りを変えるには耐力壁を壊さなければなりません。DSH は**レゴの箱**です——どのブロックも抜き出して取り替えられます。土台だと思っていたブロックでさえも。

だからこそ DSH のプラグインは「ブラウザ拡張機能」よりはるかに多くのことができます：あなたは完成品を飾り付けているのではなく、**その部品を交換している**のです。

---

## 3. プラグインはどんな姿をしているか

本当にこれだけです：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}
```

意味のある 3 行を、1 行ずつ見ていきましょう：

| この行 | 言っていること |
|---|---|
| `export const name = ...` | プラグインに名前を付ける。何か問題が起きたとき、ログで見分けられるように |
| `export function apply(ctx)` | **エントリーポイント**。フレームワークがあなたをロードするときに 1 回だけ呼び出す |
| `ctx` 引数 | システム全体とつながる**唯一の窓口**——あらゆる能力はここから受け取り、あらゆる貢献はここに差し込む |

（出典：`docs/user/develop/basic/index.zh.md`）

---

## 4. `ctx`：万能電源タップ

`ctx` は、覚えておくべき唯一の概念です。差込口がたくさんある電源タップを思い浮かべてください。それぞれの差込口が 1 種類の能力を受け持っています：

<CtxHub />

| 差込口 | 受け持つもの |
|---|---|
| `ctx.tools` | モデルが呼び出せるツール |
| `ctx.llm` | モデルアダプター（モデルの切り替えはここで） |
| `ctx.shell` | コマンド実行 |
| `ctx.fs` | ファイルの読み書き |
| `ctx.sessions` | セッション記録 |
| `ctx.skills` | スキル |
| `ctx.sandbox` | サンドボックスによる制限 |

**どちらの方向も `ctx` を通ります**：

- 他者の能力を**使う** → `ctx` から取り出す。例：`ctx.llm.stream(...)` でモデルを呼び出す
- 新しい能力を**提供する** → `ctx` に差し込む。例：`ctx.tools.register(...)` でツールを登録する

つまり「プラグインの書き方を学ぶ」とは、本質的には「自分のものを `ctx` のどの差込口に挿せばよいかを知る」ことです。第 3 章・第 2 課で `ctx` を詳しく扱い、第 3 章・第 10 課では `ctx` のキーからそれがどのパッケージにあるかを逆引きする方法を学びます。

## 5. 最も大事なルール：取り付けられるなら、きれいに取り外せなければならない

これは DSH プラグインと一般的なプラグインの最大の違いであり、その背後にある論文の核心でもあります。

一般的なソフトウェアのプラグインは、アンインストールしても「半分だけ」になりがちです：リスナーは付いたまま、タイマーは動き続け、登録したメニュー項目も残ったまま。時間が経つにつれて、システムは汚れていきます。

DSH は**登録は取り消し可能であること**を求めます——`ctx` に差し込んだものはすべて、プラグインのアンロード時にフレームワークが**自動的に**取り除きます：

> `ctx` を通じて登録されたものはすべて——イベントリスナー、ツール、タイマー——プラグインのアンロード時に自動的にクリーンアップされます。手動で removeListener や clearInterval をする必要はありません。
>
> — `docs/user/develop/basic/index.zh.md`

フレームワークが把握していないリソース（たとえばネットワーク接続）を自分で開いた場合は、`ctx.effect()` を使って閉じ方を伝えておきます：

```ts
export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('heartbeat'), 5000)
    // 返した関数は、プラグインのアンロード時に実行される
    return () => clearInterval(timer)
  })
}
```

**なぜこれがそれほど重要なのか？** それによって「動作中に自分自身を作り変える」ことが可能になるからです——再起動なしでプラグインを入れて試し、合わなければ外せば、システムはきっちり元の状態に戻ります。DSH のエージェントは**自分で自分にプラグインをインストールする**ことさえできます（第 3 章・第 8 課で扱います）。

> 💡 覚えておくのはこの一文だけで十分です：**`ctx` への登録は、どれも「元に戻す」手段を返す**。フレームワークがそれをすべて保管しておき、アンロード時にまとめて実行します。

## 6. 混同しないで：プラグイン / スキル / バンドル

初心者はこの 3 つの言葉でよく混乱します。1 つの表で整理しましょう：

| 名前 | 何か | 誰が読むか | 例 |
|---|---|---|---|
| **プラグイン（Plugin）** | `ctx` に能力を差し込む**コード** | フレームワーク | `csv` ツールを追加する |
| **スキル（Skill）** | モデルに何かのやり方を教える**マニュアル**（Markdown） | モデル | 「良い commit message の書き方」 |
| **バンドル（Bundle）** | どのプラグインをどの順でロードするかを列挙した**マニフェスト** | ランチャー | `dsh-base` がデフォルトの大きなセットを定義している |

一言でまとめると：**プラグインはシステムに部品を足し、スキルはモデルに知識を足し、バンドルは今回の起動でどの部品を組み込むかを決める。**

プラグインとスキルを兼ねるリポジトリもあります（`dsh-genui` はコードとスキルを同梱しています）。これはよくあることで、まったく問題ありません。

---

## 要点の振り返り

1. **プラグインとは `apply` をエクスポートするファイル**。フレームワークがそれを 1 回呼び出し、`ctx` を手渡してくれる。
2. **DSH に手を出せないコアはない**——モデル、ツール、UI、さらにはメインループまで、すべて対等なプラグイン。
3. **`ctx` は唯一の窓口**：能力はそこから取り出し、新しい能力はそこに差し込む。
4. **登録は取り消し可能**：`ctx` に差し込んだものはアンロード時に自動で取り除かれる。自分で開いたリソースには `ctx.effect()` を使う。
5. **プラグイン、スキル、バンドルはまったく別物**：部品 / 知識 / マニフェスト。

> 🚀 次の課：「何であるか」が分かったところで、「何ができるか」を見ていきましょう——エコシステムにある 275 個の実在のプラグインを使って、実際の限界を描き出します。
