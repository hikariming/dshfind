# 제 1 과: 플러그인이란 도대체 무엇인가?

> **한 줄 요약**: DSH 플러그인은 **`apply` 함수를 익스포트하는 파일 하나**입니다. 시작할 때 프레임워크가 `ctx`라는 「만능 멀티탭」을 건네주면, 여러분은 거기에 무언가(도구, UI, 정책)를 꽂습니다. 꽂은 것들은 플러그인이 언로드될 때 **모두 자동으로 뽑힙니다**. 핵심은 이게 전부입니다.

## 1. 이미 만나 본 플러그인에서 시작하기

아마 이런 것들은 써 보셨을 겁니다:

| 여러분이 본 것 | 하는 일 |
|---|---|
| 브라우저 확장 프로그램(광고 차단기) | 이미 완성된 브라우저에 기능을 **추가** |
| VSCode 플러그인(테마, 언어 지원) | 이미 완성된 에디터에 기능을 **추가** |
| 스마트폰 앱 | 이미 완성된 스마트폰 OS 위에 설치 |

이들에게는 공통점이 있습니다: **본체는 이미 만들어져 있고, 플러그인은 옆에 덧붙이는 패치일 뿐**이라는 것입니다. 브라우저 확장 프로그램은 주소창, 탭 바, 렌더링 엔진을 건드릴 수 없습니다——그것은 「코어」이고, 하드코딩되어 있습니다.

DSH는 다릅니다. **DSH에는 건드릴 수 없는 코어가 없습니다.**

---

## 2. DSH가 다른 점: 소프트웨어 자체가 플러그인으로 조립되어 있다

DSH 아키텍처 문서의 첫 줄에는 이렇게 적혀 있습니다:

> **모든 것은 플러그인이며, 루프도 예외가 아니다.**

「루프」란 에이전트의 메인 루프——「잠깐 생각하기 → 한 가지 행동하기 → 다시 생각하기」를 반복하는 그 사이클을 말합니다. 다른 프레임워크에서는 이것이 코어이며 바꿀 수 없습니다. DSH에서는 **이것도 플러그인**이며, 교체할 수 있습니다.

따라서 다음은 모두 플러그인이며, 완전히 대등한 위치에 있습니다:

- 어떤 모델을 쓰는지 → 플러그인
- 모델이 호출할 수 있는 모든 도구 → 플러그인
- 명령을 어디서 실행하고, 파일을 건드려도 되는지 → 플러그인
- 채팅 기록을 어디에 저장하는지 → 플러그인
- 지금 보고 있는 웹 인터페이스 → 수십 개의 플러그인
- **앞에서 말한 메인 루프** → 역시 플러그인

> 🎁 비유하자면: 다른 프레임워크는 **다 지어진 건물**입니다——구조를 바꾸려면 내력벽을 허물어야 하죠. DSH는 **레고 상자**입니다——어떤 블록이든 빼내서 바꿀 수 있습니다. 기초라고 생각했던 블록까지도요.

그래서 DSH 플러그인은 「브라우저 확장 프로그램」보다 훨씬 많은 일을 할 수 있습니다: 여러분은 완제품을 꾸미는 것이 아니라 **그 부품을 교체하는** 것입니다.

---

## 3. 플러그인은 어떻게 생겼나

정말 이만큼이 전부입니다:

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}
```

의미 있는 세 줄을 한 줄씩 살펴봅시다:

| 이 줄 | 무슨 뜻인가 |
|---|---|
| `export const name = ...` | 플러그인에 이름을 붙입니다. 문제가 생겼을 때 로그에서 알아볼 수 있도록 |
| `export function apply(ctx)` | **진입점**. 프레임워크가 여러분을 로드할 때 한 번 호출합니다 |
| `ctx` 매개변수 | 시스템 나머지 부분과 연결되는 **유일한 통로**——모든 능력은 여기서 받아 오고, 모든 기여는 여기에 꽂습니다 |

(출처: `docs/user/develop/basic/index.zh.md`)

## 4. `ctx`: 만능 멀티탭

`ctx`는 여러분이 기억해야 할 단 하나의 개념입니다. 콘센트 구멍이 여러 개 달린 멀티탭을 떠올려 보세요. 구멍 하나하나가 한 종류의 능력을 담당합니다:

<CtxHub />

| 구멍 | 담당하는 것 |
|---|---|
| `ctx.tools` | 모델이 호출할 수 있는 도구 |
| `ctx.llm` | 모델 어댑터(모델 교체는 여기서) |
| `ctx.shell` | 명령 실행 |
| `ctx.fs` | 파일 읽기와 쓰기 |
| `ctx.sessions` | 세션 기록 |
| `ctx.skills` | 스킬 |
| `ctx.sandbox` | 샌드박스 제한 |

**양방향 모두 `ctx`를 거칩니다**:

- 다른 누군가의 능력을 **사용**하려면 → `ctx`에서 꺼냅니다. 예: `ctx.llm.stream(...)`으로 모델 호출
- 새로운 능력을 **제공**하려면 → `ctx`에 꽂습니다. 예: `ctx.tools.register(...)`로 도구 등록

결국 「플러그인 작성법을 배운다」는 것은 본질적으로 「내 것을 `ctx`의 어느 구멍에 꽂아야 하는지 아는 것」입니다. 제 3 장 · 제 2 과에서 `ctx`를 깊이 다루고, 제 3 장 · 제 10 과에서는 `ctx` 키로 그것이 어느 패키지에 있는지 역으로 찾는 방법을 배웁니다.

## 5. 가장 중요한 규칙: 설치할 수 있다면, 깔끔하게 제거할 수 있어야 한다

이것이 DSH 플러그인과 일반 플러그인의 가장 큰 차이이며, 그 바탕이 된 논문의 핵심이기도 합니다.

일반 소프트웨어의 플러그인은 제거해도 「반쯤만」 제거되는 경우가 많습니다: 리스너는 그대로 붙어 있고, 타이머는 계속 돌고, 등록한 메뉴 항목도 남아 있습니다. 시간이 지나면 시스템이 지저분해집니다.

DSH는 **등록은 되돌릴 수 있어야 한다**고 요구합니다——`ctx`에 꽂은 모든 것은 플러그인이 언로드될 때 프레임워크가 **자동으로** 제거합니다:

> `ctx`를 통해 등록된 모든 것——이벤트 리스너, 도구, 타이머——은 플러그인이 언로드될 때 자동으로 정리됩니다. 수동으로 removeListener나 clearInterval을 할 필요가 없습니다.
>
> — `docs/user/develop/basic/index.zh.md`

프레임워크가 모르는 리소스(예: 네트워크 연결)를 직접 열었다면, `ctx.effect()`로 닫는 방법을 알려 주세요:

```ts
export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('heartbeat'), 5000)
    // 반환한 함수는 플러그인이 언로드될 때 실행됩니다.
    return () => clearInterval(timer)
  })
}
```

**이게 왜 그렇게 중요할까요?** 「실행 중에 스스로를 개조하는 것」을 가능하게 해 주기 때문입니다——재시작 없이 플러그인을 설치해 시험해 보고, 맞지 않으면 빼면 시스템이 정확히 원래 상태로 돌아갑니다. DSH 에이전트는 심지어 **스스로에게 플러그인을 설치**할 수도 있습니다(제 3 장 · 제 8 과에서 다룹니다).

> 💡 이 한 문장만 기억하면 충분합니다: **`ctx`에 대한 모든 등록은 「되돌리기」를 반환한다**. 프레임워크가 그것들을 모두 보관해 두었다가 언로드할 때 한꺼번에 실행합니다.

## 6. 헷갈리지 마세요: 플러그인 / 스킬 / 번들

초보자는 이 세 단어에서 자주 헷갈립니다. 표 하나로 정리해 봅시다:

| 이름 | 무엇인가 | 누가 읽는가 | 예시 |
|---|---|---|---|
| **플러그인(Plugin)** | `ctx`에 능력을 꽂는 **코드** | 프레임워크 | `csv` 도구 추가 |
| **스킬(Skill)** | 모델에게 어떤 일을 하는 방법을 가르치는 **매뉴얼**(Markdown) | 모델 | 「좋은 commit message 작성법」 |
| **번들(Bundle)** | 어떤 플러그인을 어떤 순서로 로드할지 나열한 **매니페스트** | 런처 | `dsh-base`가 기본 대형 세트를 정의 |

한 줄로 정리하면: **플러그인은 시스템에 부품을 더하고, 스킬은 모델에 지식을 더하며, 번들은 이번 부팅에서 어떤 부품을 장착할지 결정합니다.**

플러그인이면서 동시에 스킬인 저장소도 있습니다(`dsh-genui`는 코드와 함께 스킬을 번들로 제공합니다). 이는 흔한 일이며 전혀 문제없습니다.

---

## 핵심 정리

1. **플러그인은 `apply`를 익스포트하는 파일**입니다. 프레임워크가 이를 한 번 호출하면서 `ctx`를 건네줍니다.
2. **DSH에는 건드릴 수 없는 코어가 없습니다**——모델, 도구, UI, 심지어 메인 루프까지 모두 대등한 플러그인입니다.
3. **`ctx`는 유일한 통로입니다**: 능력은 여기서 꺼내고, 새 능력은 여기에 꽂습니다.
4. **등록은 되돌릴 수 있습니다**: `ctx`에 꽂은 것은 언로드 시 자동으로 제거됩니다. 직접 연 리소스에는 `ctx.effect()`를 사용하세요.
5. **플러그인, 스킬, 번들은 서로 다른 세 가지입니다**: 부품 / 지식 / 매니페스트.
