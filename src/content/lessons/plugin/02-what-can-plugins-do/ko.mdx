# 제 2 과: 플러그인으로 실제로 무엇을 할 수 있을까?

> **한 줄 요약**: "모델에 CSV를 조회하는 도구를 쥐여 주기"부터 "인터페이스 전체를 QQ2006 스킨으로 바꾸기", 나아가 "안드로이드 휴대폰에서 dsh 실행하기"까지 — **DSH의 일부라면 플러그인으로 바꿀 수 있습니다**. 이번 과에서는 생태계에 실제로 존재하는 플러그인 275개를 바탕으로 이 메커니즘의 실제 경계를 그려 봅니다.

## 1. 먼저, 판이 얼마나 큰지부터

2026년 8월 기준으로 `dsh-external` 조직에는 **수록된 플러그인 저장소가 275개** 있습니다(이 사이트의 플러그인 페이지가 바로 그 목록입니다). 태그별로 보면 가장 많이 몰린 방향은 다음과 같습니다:

| 방향 | 개수 |
|---|---|
| 인터페이스 개조(`web-ui`) | 76 |
| 모델용 도구(`tool`) | 35 |
| 스킬(`skill`) | 18 |
| 세션과 메모리(`session`) | 16 |
| 순전히 재미로(`fun`) | 15 |
| 데스크톱(`desktop`) | 10 |
| 워크플로(`workflow`) | 8 |

한 가지 패턴이 눈에 띕니다: **인터페이스 플러그인이 압도적으로 많다**는 것입니다. DSH의 Web 인터페이스 자체가 수십 개의 UI 플러그인으로 조립되어 있어서, 조각 하나를 더하거나 바꾸는 비용이 극히 낮기 때문입니다.

아래에서는 "무엇을 바꾸고 싶은가"에 따라 일곱 가지로 나누고, 각각 **실제로 존재하는 저장소**를 예로 듭니다.

---

## 2. 일곱 가지 개조와 실제 사례

### 2.1 모델에 새로운 손을 달아 주기: 도구

기본 상태의 모델은 파일 읽기/쓰기, 명령 실행, 웹 검색 정도만 할 수 있습니다. 여기에 어떤 새로운 능력이든 붙일 수 있습니다:

| 플러그인 | 모델에 주는 능력 |
|---|---|
| `dsh-tool-csv` | 의존성 없는 RFC 4180 파서로 CSV 파싱 / 조회 / 요약 |
| `dsh-latex` | 문서 작성 후 원클릭 PDF 컴파일, 구조화된 오류 위치 표시, 사이드 패널 미리보기 |
| `dsh-vision` | 임의의 OpenAI 호환 비전 모델에 연결하는 `view_image` 도구 — 모델이 "이미지를 볼" 수 있게 됨 |
| `dsh-mineru` | MineRU의 문서 파싱 능력을 모델에 노출 |
| `zotero-harvest` | 다중 소스 문헌 검색(OpenAlex / arXiv / Crossref…), 다운로드와 파싱, 로컬 Zotero로 가져오기 |

**가장 흔하고 가장 입문하기 쉬운 유형입니다** — 3과에서 직접 하나를 작성해 봅니다.

### 2.2 눈에 보이는 것을 바꾸기

DSH의 Web 인터페이스는 수십 개의 `ui-*` 플러그인을 이어 붙여 만든 것이라, 무언가를 끼워 넣기가 아주 쉽습니다:

| 플러그인 | 무엇을 바꾸는가 |
|---|---|
| `dsh-ui-whale` | 타이틀 바에 픽셀 고래가 살면서, 생각 중에는 꼬리를 흔들고 턴이 끝나면 물을 뿜음 |
| `dsh-web-panel` | UI 안에 진짜 터미널을 내장(xterm.js + node-pty) |
| `dsh-split-panes` | 분할 / 스택 패널, 패널마다 독립된 세션 |
| `dsh-custom-css` | CSS를 붙여 넣으면 즉시 스타일 변경, 설정에 저장되어 브라우저 간 동기화 |
| `dsh-genui` | 모델이 대화 안에 인터랙티브 UI를 직접 그림(차트, 폼, 퀴즈, 3D) |

### 2.3 모델이 생각하고 협업하는 방식을 바꾸기

단순히 "모델을 바꾸는" 것이 아니라, 모델이 일하는 **방식**을 바꿉니다:

| 플러그인 | 무엇을 바꾸는가 |
|---|---|
| `dsh-plan-execute` | 계획 단계에서는 추론 모델을 쓰고, 승인 후에는 자동으로 빠른 모델로 전환해 실행 |
| `dsh-advisor` | 보조 모델이 매 턴을 수동적으로 검토하고 관찰 내용을 주입 |
| `dsh-deep-research` | 적응형 딥 리서치 오케스트레이션 |
| `dsh-llm-fallbacks` | 역할별 재시도 및 폴백 모델 정책 |

### 2.4 메모리와 세션을 바꾸기

| 플러그인 | 무엇을 바꾸는가 |
|---|---|
| `dsh-memory-evolve` | 계층형 메모리(사용자 / 프로젝트 / 일일)에 더해 경험을 새로운 스킬로 증류 |
| `dsh-session-search` | 도구를 가로지르는 전문 검색(dsh / codex / claude / pi / opencode) |
| `dsh-turn-rewind` | 대화**와 워크스페이스**를 되감기, 영속적인 변경 원장으로 구동 |
| `dsh-sidechain` | `/side`로 임시 포크에서 곁가지 대화를 열어 메인 스레드를 오염시키지 않음 |

### 2.5 다른 곳에서 쓰기

DSH가 꼭 터미널 안에만 있을 필요는 없습니다:

| 플러그인 | 어디로 가는가 |
|---|---|
| `tg-bot` / `qqbot` / `dsh-feishu-bot` / `dsh-wecom-bot` | Telegram / QQ / Feishu / WeCom의 봇이 됨 |
| `dsh-vscode` | VS Code 채팅에 네이티브로 통합 |
| `dsh-browser` | 브라우저를 직접 조작하는 Chrome 사이드 패널 확장 |
| `dsh-android` | 안드로이드 휴대폰에서 실행 |
| `dsh-desktop-electron` | 트레이에 상주하는 크로스 플랫폼 데스크톱 셸 |

### 2.6 순전히 재미로

이 유형에만 저장소가 15개나 된다는 것은 진입 장벽이 얼마나 낮은지를 잘 보여 줍니다:

| 플러그인 | 무엇을 하는가 |
|---|---|
| `dsh-pet` | DSH를 닫아 두어도 세션 상태를 감지하고 효과음으로 알려 주는 데스크톱 고래 |
| `7d7d` | 레트로 미니게임 포털, 모델이 생성한 게임을 UI 안에서 바로 플레이 |
| `dsh-gomoku` | AI와 오목을 두거나, AI 둘이 서로 대국하게 하기 |
| `dsh-lazyfish` | 오른쪽 "딴짓" 패널: 피드와 Bilibili 플레이어 |
| `dsh-qq2006` | QQ2006 풀 스킨 |

### 2.7 밑바닥 부품을 교체하기

이 유형이 "커널이 없다"는 것을 가장 잘 보여 줍니다 — 실행 기반 자체를 갈아 끼우는 것이죠:

- **명령 실행 백엔드** 교체(로컬 / 샌드박스 / PowerShell / 원격 샌드박스)
- **세션 저장소** 교체(JSONL / SQLite / 관계형 데이터베이스)
- **샌드박스 구현** 교체(bwrap / Landlock / Seatbelt / microsandbox)
- **서브에이전트 드라이버** 교체(인프로세스 / ACP / Codex / Claude Code)

이것들은 공식 저장소에 함께 제공되며, 설정 한 줄만 바꾸면 전환됩니다.

## 3. 그렇다면 *불가능한* 것은?

능력을 자랑하는 것보다 경계를 분명히 하는 편이 더 쓸모 있습니다.

**① 플러그인은 "물리 법칙"을 바꿀 수 없습니다.** 프로토콜 상수, 외부 API 규격, 보안 불변 조건은 고정되어 있습니다 — 샌드박스가 거부한 파일 작업을 "빠져나가게" 만들 수는 없습니다. 거부는 정책의 결과이지 버그가 아닙니다.

**② 일부 능력은 설계상 옵트인입니다.** 가장 분명한 사례는 자기 참조 도구 세트 `tool-cordis`로, 모델이 실행 중에 자기 자신에게 새 플러그인을 마운트할 수 있게 해 줍니다. 공식 입장은 명확합니다:

> 이 도구 세트는 명시적으로 활성화해야 하며, bash 도구를 부여할 때와 같은 신중함이 필요합니다.

이유는 단순합니다: 모델이 작성한 플러그인 코드는 여러분이 실행 중인 프로세스에 실제로 들어갑니다. 기본으로 포함하지 않는 것이 옳은 판단입니다.

**③ 플러그인끼리 완전히 격리되어 있지는 않습니다.** 같은 슬롯을 두고 다투는 두 플러그인은 충돌합니다 — 예를 들어 둘 다 유일한 세션 제목 생성기가 되려는 경우입니다. DSH의 답은 나중 것이 조용히 이기게 두는 대신 **로드 시점에 요란하게 실패하는** 것입니다. 이것이 "잘못된 설정은 요란하게 실패한다"는 원칙이며, 이는 기능입니다: 일찍 실패하는 편이 실행 도중에 이상하게 동작하는 것보다 훨씬 낫습니다.

**④ 모든 것이 플러그인으로 만들 가치가 있지는 않습니다.** 공식 규칙이 하나 있습니다 — 직접 만들기보다 잘 유지 관리되는 의존성을 우선하라는 것입니다. 성숙한 라이브러리가 여러분이 떠안아야 할 코드와 테스트를 실제로 없애 준다면 라이브러리를 쓰는 것이 맞습니다.

## 4. 찾기와 설치하기

**찾기**:

- 이 사이트의 [플러그인 페이지](/plugins) — 275개 저장소를 카테고리별로 필터링 가능
- `dsh-hub` / `dsh-plus` — 커뮤니티가 엄선한 목록
- `marisa`(일명 dshx) — GitHub topic으로 자동 탐색하는 외부 플러그인 매니저

**설치하기**: 대부분의 플러그인 README에 한 줄짜리 명령이 있습니다. 공식 방법은 profile에 추가하는 것입니다:

```sh
dsh plugin --profile web add <package or local path>
```

설치하고 나면 `cordis.yml`에 해당 항목이 보입니다. 빼고 싶으면 그 줄을 지우면 됩니다 — **1과의 규칙으로 돌아가 봅시다: 설치할 수 있으면, 제거할 수도 있다.**

> 💡 실용적인 제안: "모델에 도구 주기" 유형의 플러그인부터 시작해 보세요(예: `dsh-toolkit`에 들어 있는 의존성 없는 유틸리티 6개). UI도 기반도 건드리지 않으므로 문제가 생겨도 영향 범위가 가장 작습니다.

## 핵심 정리

1. **실제 플러그인 275개**, 가장 많은 것은 인터페이스 개조(76), 모델용 도구(35), 스킬(18).
2. **일곱 가지 개조 방향**: 도구 추가, UI 변경, 모델의 협업 방식 변경, 메모리와 세션 변경, 실행 장소 변경, 순수한 재미, 기반 부품 교체.
3. **인터페이스 플러그인이 가장 많은** 이유는 Web UI 자체가 수십 개의 UI 플러그인으로 이루어져 있어 한계 비용이 아주 작기 때문.
4. **경계는 실재합니다**: 프로토콜과 보안 불변 조건은 고정, 자기 참조 도구 세트는 기본적으로 꺼짐, 충돌은 로드 시점에 실패.
5. **설치도 제거도 설정 변경일 뿐** — `cordis.yml`에서 해당 줄을 지우면 원래 상태로 돌아갑니다.
